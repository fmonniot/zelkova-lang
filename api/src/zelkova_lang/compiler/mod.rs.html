1//! The Zelkova compiler
2//!
3//!
4//!# How to compile a package ?
5//!
6//! Note: We don't manage interfaces and external modules. We try to keep them
7//! in mind, so they can be relatively easily added later on.
8//!
9//! 1. Start at the src/ folder. We name it root. (later on defined in a `zelkova.toml` manifest)
10//! 2. Collect all `*.zelkova` files with their path name relatives to the root.
11//! 3. Create a `SourceFiles` mapping from `ModuleName` to `parser::Module`.
12//!     1. module names are deduced from file name
13//!     2. parsing is done through `parser::parse`
14//!     3. Verify that `parser::Module.name` match the one from the file system
15//! 4. Build a dependency graphs from the modules import
16//!     1. build it
17//!     2. Verify there is no cyclic relation between modules
18//! 5. Following the deps graph,
19//!     1. canonicalize each modules
20//!     1. check each module (type check, exhaustiveness, etc…)
21//!     1. Bonus point to parallelize the tree branches which are not dependent on each others
22//! 6. Once we have a module with all checks passing, create its interface and emit AST/interface
23//! 7. Report. Each phase returns every error it found, `check_module` tags those with
24//!    the module they came from, and `compile_package` accumulates them across modules
25//!    and renders them all through `CompilationError::as_diagnostic` — the one place a
26//!    `Diagnostic` is built. See the `PhaseError` trait for what a phase error owes it.
27//!

108/// A byte span paired with the file it was written in.
109///
110/// [`NodeSpan`] is enough for an error about the module a phase is currently
111/// checking, because [`compile_package`] supplies that one file id for the whole
112/// diagnostic at render time (see [`PhaseError`] and [`SpanLabel`]). A span pulled
113/// out of an [`Interface`] cannot rely on that: it was written in the *exporting*
114/// module's file, which is not necessarily the file being rendered, so the id has
115/// to travel with the span instead of being attached later. This is that pair —
116/// [`Interface::source_span`] is how one gets built.
117#[derive(Debug, Clone, Copy, PartialEq)]
118pub struct SourceSpan {
119    pub file: SourceFileId,
120    pub span: Span<BytePos>,
121}

123/// An interface is trim down version of a module.
124///
125/// We use it when translating a local source AST into its canonical form as
126/// an optimization technique. Instead of parsing every source files on each
127/// file compilation, we save the publicly exposed information of a successfully
128/// parsed module and only load this information on module depending on it.
129///
130/// All `Interface` indices are using non-qualified names. To get the qualified
131/// version, simply use `I.module_name.qualify_name(&name)`.
132// TODO Union types will need a way to reflect that some type constructor are private
133#[derive(Debug)]
134pub struct Interface {
135    pub module_name: ModuleName,
136    /// Each value's type, paired with where its declaration (annotation and body
137    /// together) was written — [`canonical::Value::span`] — so a diagnostic about a
138    /// name found here can point at the declaration, not just name it.
139    pub values: HashMap<Name, (NodeSpan, canonical::Type)>,
140    pub unions: HashMap<Name, canonical::UnionType>,
141    // TODO type aliases
142    //aliases: HashMap<Name, >
143    /// infixes is a map from the operator symbol to its information
144    pub infixes: HashMap<Name, canonical::Infix>,
145    /// The file this interface's module was read from, when the caller knows it.
146    ///
147    /// It is what makes a diagnostic about an imported name able to underline that
148    /// name's *own* source rather than merely naming its module. Nothing inside a
149    /// module check can supply it: a phase only ever sees one module and never
150    /// learns its [`SourceFileId`] (see [`PhaseError`]). Driver code does, so
151    /// [`canonical::Module::to_interface`] takes it as an argument, and its one
152    /// caller — [`dependencies::ModuleWalker::check_in_order`], which like
153    /// [`compile_package`] is a driver loop and already holds the file each module
154    /// came from — passes it there. A hand-built interface, as every test below
155    /// `check_module` constructs, passes `None`; [`Interface::source_span`] then has
156    /// no file to pair a span with and returns `None`, so the diagnostic degrades to
157    /// no secondary label rather than a wrong one.
158    pub file: Option<SourceFileId>,
159}
160
161impl Interface {
162    /// Pair a [`NodeSpan`] taken from this interface's own data — a value's
163    /// declaration, a [`canonical::UnionType`]'s or [`canonical::Infix`]'s `span`
164    /// field — with the file it was written in, when both halves are known.
165    ///
166    /// Both halves are needed: a `NodeSpan` with nothing behind it (a hand-built
167    /// test value) or an interface with no attached file (same) leaves nothing
168    /// honest to build, and `None` is that answer — the caller renders no label
169    /// rather than one pointing at byte 0 of the wrong file.
170    pub fn source_span(&self, span: NodeSpan) -> Option<SourceSpan> {
171        match (self.file, span.span()) {
172            (Some(file), Some(span)) => Some(SourceSpan { file, span }),
173            _ => None,
174        }
175    }
176}

178/// One underlined region of the user's source, and what to say about it.
179///
180/// # `file`: when a label is not about the module under check
181///
182/// A [`codespan_reporting::Label`] needs a file id as well as a byte range. Most
183/// labels don't carry one themselves: a phase only ever sees one module, so its
184/// spans belong to the file that module was read from, and [`compile_package`] —
185/// the only place that knows which file that is — supplies it for the whole
186/// diagnostic at render time. `file: None` is that case, and it covers everything
187/// built before `ERR-5`.
188///
189/// `Some` is the escape hatch: a label built from a [`SourceSpan`] cloned out of an
190/// [`Interface`] (via [`Interface::source_span`]) already carries its own file,
191/// generally a *different* one from the module being checked — "the annotation you
192/// are contradicting is over there, in `Basics`" — and that id is used verbatim
193/// instead of the diagnostic's.
194///
195/// `primary` is the rustc distinction, and it applies independently of `file`: the
196/// caret under the thing that is wrong is primary even when it is local, and
197/// "defined here" in another file is secondary even though it is the only label
198/// pointing into that file.
199#[derive(Debug, Clone, PartialEq)]
200pub struct SpanLabel {
201    pub span: Span<BytePos>,
202    pub message: String,
203    pub primary: bool,
204    pub file: Option<SourceFileId>,
205}

207/// What a compiler phase owes the diagnostic reporter.
208///
209/// Each phase keeps its own error type — one enum for the whole compiler would make
210/// every phase depend on the vocabulary of every other. What they have to share is
211/// the ability to describe themselves in the user's terms, because
212/// [`CompilationError::as_diagnostic`] is the only place a `Diagnostic` is ever
213/// built and it has no phase-specific knowledge to fall back on. Dumping
214/// `format!("{:?}", e)` into a note is exactly what this trait replaces: a `Debug`
215/// dump names Rust types, not source constructs.
216///
217/// # How much a span can say, and where that stops
218///
219/// Every production in `grammar.lalrpop` that builds a node captures `@L`/`@R`, so
220/// declarations, expressions, patterns and types all know where they were written,
221/// and canonicalization copies that onto the node it builds. An error raised from one
222/// of those construction sites returns a [`SpanLabel`] from
223/// [`labels`](PhaseError::labels) and gets a caret under the text it is about — an
224/// unresolvable name is underlined at the identifier, not across the declaration
225/// containing it.
226///
227/// Not every error can. `labels` defaults to empty and that is a real answer, not a
228/// stub: an error raised while walking a node the grammar does not span — an
229/// `exposing` list, say — has nowhere to point, and renders as message-plus-notes
230/// with no caret, exactly as every phase after parsing used to. An error that groups
231/// others (`canonical::Error::Many`, `EnvironmentErrors`) has no position of its own
232/// and flattens its members' labels instead, the way it already flattens their
233/// messages.
234///
235/// The typer is the phase that has to work for this, and it does: it does not check
236/// the canonical AST but a term language of its own, so it carries each canonical
237/// node's span into that language, each constraint records the term and the *reason*
238/// it came from, and `unify` reports the origin of the constraint it failed on. A
239/// type error therefore underlines the sub-expression that disagrees and adds a
240/// secondary label under the annotation that says what was expected (`ERR-4`).
241///
242/// `parser::Error` is still the one phase error that does not go through this trait
243/// at all — it builds its own labelled `Diagnostic` through `parser::Error::diagnostic`.
244///
245/// # The two ways a label learns its `SourceFileId`
246///
247/// A phase still never knows the id of the file the module it is checking came
248/// from — that half is unchanged, and stays attached by `compile_package`, the only
249/// place that knows it, the way `CompilationError::Source` already works. A
250/// [`SpanLabel`] with `file: None` — everything built before `ERR-5` — means
251/// exactly that: "in the module under check", resolved at render time.
252///
253/// That is right for an error entirely about one module and cannot cover a
254/// diagnostic that also names something written elsewhere — "the annotation you
255/// are contradicting is over there, in `Basics`". For that, `file` carries its own
256/// [`SourceFileId`] instead, taken from a [`SourceSpan`] cloned out of an
257/// [`Interface`] via [`Interface::source_span`]. An `Interface` can offer that
258/// because it is not a phase: it is built by driver code
259/// (`dependencies::ModuleWalker::check_in_order`) that already has the file the
260/// module it just checked came from, and stamps it onto the `Interface` before
261/// handing it to whoever imports next. `canonical::Type` still carries no span of
262/// its own — seeing why is worth a look at that type's own documentation.
263pub trait PhaseError {
264    /// One line naming what went wrong, in the vocabulary of the user's source.
265    ///
266    /// This is rendered as the diagnostic's headline, so it has to read on its own:
267    /// no `{:?}`, no Rust type names.
268    fn message(&self) -> String;
269
270    /// Supporting detail, one string per rendered note. Empty by default.
271    fn notes(&self) -> Vec<String> {
272        Vec::new()
273    }
274
275    /// The regions of the user's source this error is about, if it knows any.
276    ///
277    /// Empty — the default — means this error has no position to point at, and it
278    /// renders as message-plus-notes with no caret. See the trait's documentation.
279    fn labels(&self) -> Vec<SpanLabel> {
280        Vec::new()
281    }
282
283    /// This error's message followed by its notes.
284    ///
285    /// A `Diagnostic` has one headline, so an error that ends up inside a group —
286    /// several errors from one phase, or a variant like `canonical::Error::Many`
287    /// that wraps others — has to give up its headline and become notes. This is
288    /// that demotion, in one place, so a group cannot silently drop the message of
289    /// a member it swallowed.
290    fn message_and_notes(&self) -> Vec<String> {
291        std::iter::once(self.message())
292            .chain(self.notes())
293            .collect()
294    }
295}

297/// Turn `SpanLabel`s into the `codespan_reporting::Label`s a `Diagnostic` renders.
298///
299/// `fallback` is the file a label with none of its own resolves to — the module
300/// currently being checked, when the caller has one. So `fallback` is a fallback
301/// rather than a gate: a label needs *some* file, because a byte range on its own
302/// does not say which file to underline, but a [`SpanLabel`] carrying its own
303/// [`SpanLabel::file`] already has one and renders whether or not `fallback` is
304/// `Some`. Only a label with neither is a byte range nobody can place, and that one
305/// is dropped rather than guessed at.
306///
307/// This is the one place that distinction is applied; both [`phase_diagnostic`] (a
308/// fallback file, from the module under check) and the dependency-cycle arm of
309/// `CompilationError::as_diagnostic_in` (no fallback — a cycle has no single
310/// module) go through it.
311fn spans_to_labels(
312    labels: Vec<SpanLabel>,
313    fallback: Option<SourceFileId>,
314) -> Vec<Label<SourceFileId>> {
315    labels
316        .into_iter()
317        .filter_map(|l| {
318            // A label with its own file — a `SourceSpan` cloned out of an
319            // `Interface`, or (`ERR-6`) a `CycleEdge`'s file — points into that
320            // file instead of falling back. That is the whole mechanism `ERR-5`
321            // adds: everything built before it left `file` `None` and relied on
322            // `fallback` here.
323            let label_file = l.file.or(fallback)?;
324            let range = l.span.to_range();
325            let label = if l.primary {
326                Label::primary(label_file, range)
327            } else {
328                Label::secondary(label_file, range)
329            };
330            Some(label.with_message(l.message))
331        })
332        .collect()
333}

335/// Render the errors one phase produced for one module.
336///
337/// A `Diagnostic` has room for exactly one headline, so a lone error gets to be that
338/// headline and a group is summarised instead, with every message demoted to a note.
339/// `phase` names the phase in that summary line ("canonical", "type", …).
340///
341/// `file` is the module's source file when the caller knows it, and it is handed
342/// straight to [`spans_to_labels`] as the fallback that document describes: a label
343/// of its own — the cross-module ones `ERR-5` added — renders regardless, so a
344/// `CompilationError` built by hand, as the tests in this module do, loses only the
345/// labels about the module under check. `compile_package` always wraps in
346/// [`CompilationError::InFile`] and so loses none.
347///
348/// Both branches attach labels: only the headline demotion differs between one error
349/// and a group, and an error that got swallowed into a note still knows where it was.
350fn phase_diagnostic<E: PhaseError>(
351    module: &Name,
352    phase: &str,
353    errors: &[E],
354    file: Option<SourceFileId>,
355) -> Diagnostic<SourceFileId> {
356    let labels =
357        |errors: &[E]| spans_to_labels(errors.iter().flat_map(|e| e.labels()).collect(), file);
358
359    match errors {
360        [only] => Diagnostic::error()
361            .with_message(format!("[{}] {}", module, only.message()))
362            .with_labels(labels(errors))
363            .with_notes(only.notes()),
364        many => Diagnostic::error()
365            .with_message(format!(
366                "[{}] {} {} error{}",
367                module,
368                many.len(),
369                phase,
370                if many.len() == 1 { "" } else { "s" }
371            ))
372            .with_labels(labels(many))
373            .with_notes(many.iter().flat_map(|e| e.message_and_notes()).collect()),
374    }
375}

377/// Every way compiling a package can fail, tagged with the phase that failed.
378///
379/// Each phase-carrying variant holds *all* the errors that phase produced for one
380/// module rather than only the first, plus the module's [`Name`], which is what
381/// `as_diagnostic` puts in front of the message. Rendering goes through
382/// [`PhaseError`]; see that trait for why no variant here carries a span.
383#[derive(Debug)]
384pub enum CompilationError {
385    LoadingFiles(Vec<SourceFileError>),
386    Source(parser::Error, SourceFileId),
387    Canonical(Vec<canonical::Error>, Name),
388    /// Type checking failed for the named module.
389    Type(Vec<typer::Error>, Name),
390    /// Exhaustiveness checking failed for the named module. Unreachable while
391    /// `exhaustiveness::check` is a stub, but rendered like any other phase.
392    Exhaustiveness(Vec<exhaustiveness::Error>, Name),
393    DependenciesError(dependencies::Error),
394
395    /// An error together with the file the module it belongs to was read from.
396    ///
397    /// A phase never knows its [`SourceFileId`], so the labels its errors produce are
398    /// byte ranges with no file attached. This is where the two halves are put
399    /// together, and it has exactly one constructor: [`compile_package`], which is
400    /// the only place that knows which file a module was parsed from. Nothing else
401    /// should build it — an id guessed anywhere else would underline the wrong file.
402    InFile(Box<CompilationError>, SourceFileId),
403
404    /// Every error accumulated over one compilation pass.
405    ///
406    /// `compile_package` does not stop on the first failure: it keeps going so that
407    /// one broken module cannot hide the diagnostics of the others. This variant is
408    /// how that accumulation becomes a failure again at the end of the pass, with the
409    /// typed errors still intact for the caller to inspect.
410    Many(Vec<CompilationError>),
411}
412
413impl CompilationError {
414    /// Turn this error into the diagnostic the user reads.
415    ///
416    /// This is the compiler's single rendering point — `compile_package` calls it
417    /// and nothing else builds a `Diagnostic` from a phase error. It is public so
418    /// that a test can assert on what the user is actually shown, rather than on
419    /// `is_err()`: what a failure *says* is the behaviour this method exists for.
420    pub fn as_diagnostic(&self) -> Diagnostic<SourceFileId> {
421        self.as_diagnostic_in(None)
422    }
423
424    /// The name of the module this error belongs to, when it has one.
425    ///
426    /// `compile_package` uses it to look up the file the module was read from, which
427    /// is how an [`InFile`](CompilationError::InFile) wrapper gets its id.
428    pub fn module(&self) -> Option<&Name> {
429        match self {
430            CompilationError::Canonical(_, module)
431            | CompilationError::Type(_, module)
432            | CompilationError::Exhaustiveness(_, module) => Some(module),
433            CompilationError::InFile(inner, _) => inner.module(),
434            _ => None,
435        }
436    }
437
438    /// `as_diagnostic`, carrying the file the error's module was read from.
439    ///
440    /// `file` is `None` until an [`InFile`](CompilationError::InFile) wrapper supplies
441    /// one, which only `compile_package` builds. Everything downstream of that
442    /// distinction is in `phase_diagnostic`, where it serves as the fallback file for
443    /// labels that do not name one themselves.
444    fn as_diagnostic_in(&self, file: Option<SourceFileId>) -> Diagnostic<SourceFileId> {
445        match self {
446            // The one arm that changes `file`, and the only one that can: it is the
447            // only variant that carries an id.
448            CompilationError::InFile(inner, id) => inner.as_diagnostic_in(Some(*id)),
449            // The one phase that carries spans renders its own labelled diagnostic.
450            CompilationError::Source(err, file_id) => err.diagnostic(*file_id),
451            // Loading failures are not attached to a module — there is no module yet,
452            // and each error names its own file instead.
453            CompilationError::LoadingFiles(errors) => Diagnostic::error()
454                .with_message("Error while loading the package files")
455                .with_notes(errors.iter().flat_map(|e| e.message_and_notes()).collect()),
456            CompilationError::Canonical(errors, module) => {
457                phase_diagnostic(module, "canonical", errors, file)
458            }
459            CompilationError::Type(errors, module) => {
460                phase_diagnostic(module, "type", errors, file)
461            }
462            CompilationError::Exhaustiveness(errors, module) => {
463                phase_diagnostic(module, "exhaustiveness", errors, file)
464            }
465            // A dependency cycle belongs to the package, not to any one module, so it
466            // does not go through `phase_diagnostic` — there is no module to supply
467            // the fallback file that helper takes. Its labels don't need one: each
468            // `CycleEdge` (`ERR-6`) carries the file the `import` forming it was
469            // written in, so `spans_to_labels` is called with `None` and a label
470            // with no file of its own (an edge `ModuleWalker::new` couldn't map back
471            // to a file) is dropped rather than guessed at.
472            CompilationError::DependenciesError(err) => Diagnostic::error()
473                .with_message(err.message())
474                .with_labels(spans_to_labels(err.labels(), None))
475                .with_notes(err.notes()),
476            // `compile_package` renders each accumulated error individually rather than
477            // wrapping first, so this arm only fires when a `Many` is rendered as a
478            // whole. It summarises rather than repeating what those diagnostics said.
479            //
480            // This is the one group that deliberately does not flatten its members'
481            // labels. The phase-error groups that do — `canonical::Error::Many`,
482            // `EnvironmentErrors` — hold errors from a single module, so their labels
483            // all belong to one file and the group is the *only* thing rendered. This
484            // one spans the whole package: its members are `InFile` wrappers naming
485            // different files, and each has already been rendered with its own carets
486            // by the time this summary is built. Flattening here would draw every
487            // caret in the package a second time under one headline.
488            CompilationError::Many(errors) => Diagnostic::error()
489                .with_message(format!(
490                    "compilation failed with {} error{}",
491                    errors.len(),
492                    if errors.len() == 1 { "" } else { "s" }
493                ))
494                .with_notes(
495                    errors
496                        .iter()
497                        .map(|e| e.as_diagnostic_in(file).message)
498                        .collect(),
499                ),
500        }
501    }
502
503    fn from(err: parser::Error, source_id: SourceFileId) -> Self {
504        CompilationError::Source(err, source_id)
505    }
506}

508// There is deliberately no `From<typer::Error>` or `From<exhaustiveness::Error>`
509// here. Both used to exist and neither could be written honestly: a `CompilationError`
510// needs the name of the module its error belongs to, and a phase error does not know
511// it. `From` has nowhere to get it from, so the two impls lost information instead —
512// one discarded the error and the other panicked. `check_module` is the one place that
513// knows both halves, so that is where the conversion happens (see `ERR-2` in
514// `docs/tickets/README.md`).
515
516impl From<dependencies::Error> for CompilationError {
517    fn from(err: dependencies::Error) -> Self {
518        CompilationError::DependenciesError(err)
519    }
520}

523    fn from(errors: Vec<SourceFileError>) -> Self {
524        CompilationError::LoadingFiles(errors)
525    }

528// TODO Ultimately we will pass a manifest content instead of a raw path
529// (eg. something akin to elm.json or package.json)
530pub fn compile_package(package_path: &Path) -> Result<(), CompilationError> {
531    // Error reporter
532    let mut writer = StandardStream::stderr(ColorChoice::Auto);
533    let config = codespan_reporting::term::Config {
534        tab_width: 2,
535        ..codespan_reporting::term::Config::default()
536    };
537
538    // Reports the outcome of one phase on stderr. Failing to write a status line is
539    // not itself a compilation failure, so the write results are deliberately
540    // discarded rather than unwrapped.
541    let mut print_status = |success: bool, text: String| {
542        let (color, label) = if success {
543            (Color::Green, "success")
544        } else {
545            (Color::Red, "failure")
546        };
547        let _ = writer.set_color(ColorSpec::new().set_bold(true).set_fg(Some(color)));
548        let _ = write!(&mut writer, "{}", label);
549        let _ = writer.reset();
550        let _ = writeln!(&mut writer, " {}", text);
551    };
552
553    // Step 1: package_path parameter
554
555    // Step 2 and 3.a
556    debug!("phase: load package sources");
557    // Loading is the one phase whose errors cannot be deferred: without the loaded
558    // files there is no `Files` database to render any diagnostic against, this one
559    // included. It is returned unrendered and the caller reports it.
560    let sources = source::load_package_sources(package_path)?;
561
562    // Further steps will produce errors. We aggregate them here and report them at the
563    // end of the compilation phase, rather than stopping on the first one, so that a
564    // single broken module doesn't hide the diagnostics of every other module.
565    //
566    // They are kept as typed `CompilationError`s and not as already-rendered
567    // `Diagnostic`s for two reasons: `as_diagnostic` stays the single rendering point,
568    // and the accumulation is still meaningful as a return value — an empty vector is
569    // what makes this function return `Ok`.
570    let mut errors: Vec<CompilationError> = vec![];
571
572    // Step 3.b
573    debug!("phase: parse package sources");
574    let mut modules: Vec<parser::Module> = vec![];
575    // Which file each module was parsed from. This is the only point in the compiler
576    // where both halves are in scope at once — a phase is handed a module and never
577    // learns where it came from — so the mapping is recorded here and used below to
578    // wrap the check errors in `InFile`, which is what lets their labels render.
579    let mut module_files: HashMap<Name, SourceFileId> = HashMap::new();
580    let mut parse_failures = 0;
581    for (id, file) in sources.iter() {
582        match parser::parse(file.file()) {
583            Ok(module) => {
584                module_files.insert(module.name.clone(), id);
585                modules.push(module);
586            }
587            Err(err) => {
588                parse_failures += 1;
589                errors.push(CompilationError::from(err, id));
590            }
591        }
592    }
593
594    if parse_failures == 0 {
595        print_status(true, format!("parsed {} modules", modules.len()));
596    } else {
597        print_status(
598            false,
599            format!(
600                "parsed {} modules, {} failed to parse",
601                modules.len(),
602                parse_failures
603            ),
604        );
605    }
606
607    // Step 3.c
608    // TODO Verify modules name match file system.
609    // TODO Include this into the parser::parse() function (w/ module name as argument) ?
610
611    debug!("phase: Build module dependency graph");
612    // Step 4
613    // A cycle leaves us with no order to check the modules in, so the check phase is
614    // skipped — but the error goes through the same reporting path as the others
615    // instead of returning early unrendered.
616    let walker = match dependencies::ModuleWalker::new(&modules, &module_files) {
617        Ok(walker) => Some(walker),
618        Err(err) => {
619            errors.push(err.into());
620            None
621        }
622    };
623
624    // TODO Load those information from somewhere
625    let package_name = PackageName::new("zelkova", "core");
626    let mut interfaces = std::collections::HashMap::new();
627
628    debug!("phase: Check modules");
629
630    // Step 5: Follow graph and call check_module on each
631    if let Some(walker) = walker {
632        // `check_in_order` checks every module regardless of earlier failures and
633        // hands back both halves: the modules that checked, and the errors from the
634        // ones that didn't (see `docs/tickets/README.md`, `BUG-2`). Both are reported
635        // here, and the errors still flow into `errors` below so a failing module
636        // keeps making this function return `Err` — only the previously-discarded
637        // successes are new.
638        //
639        // `module_files` is also how each checked module's `Interface` learns which
640        // file it came from (`Interface::file`, `ERR-5`): this is the one place that
641        // knows both the module and its file, so `check_in_order` takes the map and
642        // stamps it onto every interface it inserts as it goes.
643        let (can_mods, check_errors) =
644            walker.check_in_order(&package_name, &mut interfaces, &module_files, check_module);
645
646        if check_errors.is_empty() {
647            print_status(
648                true,
649                format!(
650                    "checked modules: {:#?}",
651                    can_mods
652                        .iter()
653                        .map(|m| m.name.as_human_string())
654                        .collect::<Vec<_>>()
655                ),
656            );
657        } else {
658            print_status(
659                false,
660                format!(
661                    "checked modules: {:#?} ({} failed to check)",
662                    can_mods
663                        .iter()
664                        .map(|m| m.name.as_human_string())
665                        .collect::<Vec<_>>(),
666                    check_errors.len()
667                ),
668            );
669            // Tag each error with the file its module was read from, so the spans its
670            // phase produced have something to point into. A module with no entry —
671            // there is none today, since only a module that parsed can be checked —
672            // stays unwrapped and renders exactly as it did before spans existed.
673            errors.extend(check_errors.into_iter().map(|error| {
674                match error.module().and_then(|name| module_files.get(name)) {
675                    Some(id) => CompilationError::InFile(Box::new(error), *id),
676                    None => error,
677                }
678            }));
679        }
680    }
681
682    // Step 6
683    // emit interfaces and generate code
684    debug!("phase: codegen");
685
686    // Step 7: report everything we accumulated, then let that accumulation decide the
687    // return value. Rendering the errors and returning `Ok` regardless was `BUG-1`.
688    for error in &errors {
689        // A rendering failure must not mask the compilation failure we are about to
690        // return, and there is nowhere left to report it to, so it is dropped.
691        let _ = term::emit_to_write_style(
692            &mut writer.lock(),
693            &config,
694            &sources,
695            &error.as_diagnostic(),
696        );
697    }
698
699    if errors.is_empty() {
700        Ok(())
701    } else {
702        Err(CompilationError::Many(errors))
703    }
704}

706/// Take a parsed module file within the ecosystem and apply all checks to it
707///
708/// TODO canonicalization must happens before checkings, because type check (at least)
709/// will require access to other modules canonical representation.
710/// That probably mean moving the `canonical::canonicalize` call out of this function
711pub fn check_module(
712    package: &PackageName,
713    interfaces: &HashMap<Name, Interface>,
714    source: &parser::Module,
715) -> Result<canonical::Module, CompilationError> {
716    // - desugar ~?~ *!*
717    // Should I have an intermediate AST before type checking ?
718    // This could actually be useful to have something optimized for
719    // the type checker. It would also be something that can be used
720    // as an information dump for dependencies (keep types solved as
721    // a result and don't type checks those modules more than once).
722    //
723    // Each phase accumulates its own errors and hands back all of them; this is where
724    // they are tagged with the module they came from, because a phase only ever sees
725    // one module and has no reason to carry its name around.
726    let canonical = canonical::canonicalize(package, interfaces, source)
727        .map_err(|errors| CompilationError::Canonical(errors, source.name.clone()))?;
728
729    // - type checking and inference
730    // TODO Here either type checks return the new types, or it take a mutable canonical
731    // representation and "fill the blank" directly on the canonical AST.
732    typer::type_check(&canonical)
733        .map_err(|errors| CompilationError::Type(errors, source.name.clone()))?;
734
735    // verify in pattern matching branches that all variants are covered
736    exhaustiveness::check(&canonical)
737        .map_err(|errors| CompilationError::Exhaustiveness(errors, source.name.clone()))?;
738
739    Ok(canonical)
740}
